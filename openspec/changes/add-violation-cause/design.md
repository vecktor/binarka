# Design: add-violation-cause

## Context

The requirements are signed (FR-120, A-58, FR-64, FR-65 and FR-70 amended; the user's signature of 2026-10-11, CQ-1 A and the defaults). The reasoning behind them is the draft `docs/handoff/violation-cause-amendment-draft-2026-10-11.md` and is not repeated here. This folder is the slice that builds it: the marker in `src/ui/play-page.ts`, the suffix in `src/ui/strings.ts`, the mark in `src/ui/style.css`. The design touch is already made: `design/v0/app/binarka.css` (lines 778-794) holds `.cell-cause` and `.cell-cause::after`, the user adopted the review's forced-colours rule and kept the mark's size (`docs/design/cause-touch-2026-10-11/REVIEW.md`, the user's answers). The page has no database and no server (TC-12); the marker is never stored.

## Goals

- After every board change of one cell X, X carries `cell-cause` exactly when the checker's cells include X; no other cell does; the class is removed by every later board change and by nothing else (FR-120).
- The cell's accessible name carries «, спричиняє порушення» after «, підказка», and follows the marker (FR-70).
- The mark is a corner triangle in `--color-violation-border` with a `0.5rem` floor, with no new token and no new width (FR-64, FR-65, A-58).
- No NFR-14 shot moves; the two design freezes change in provenance only.

## Non-goals

- A 3px border, a rounded mark, motion, `aria-describedby`, a mark at mount, a bigger mark at 8×8 on 320px (all decided: draft CQ-1 to CQ-3, the user's answers).
- Real forced-colours rendering tests (A-28, TC-13); the ", hint" / ", hinted" mismatch of FR-70 (CQ-6).
- Any change to the engine, the highlight set or the hint.

## Decisions

1. **The predicate reads the checker's cells, not the page's highlight set (ADR-worthy? no: A-58 already ratifies it; flagged because it narrows row 159).** `cause = findViolations(board).some((v) => v.cells.some(([r, c]) => r === X.r && c === X.c))`. `refreshHighlights` expands a count violation to the whole line (`play-page.ts:252-254`), so reusing its `marked` set would mark a correct 0 put into an overfull row (P3, CQ-3 A). The implementer must call the checker's `v.cells` and not the `marked` set. Trade-off: the checker runs once more per press unless `refreshHighlights` hands back its list; the cost is one `findViolations` on at most 64 cells, negligible, and sharing the list is the implementer's choice. The spec pins behaviour (P3, the oracle sweep), not structure. No before/after comparison is needed: X has just changed, so a violation that contains it cannot be one that was there before (the draft's finding 2: 1.2 million random one-cell changes, no disagreement).
2. **State: `cause: [row, col] | null` beside `hinted`, with a `setCause` that mirrors `setHinted`.** `setHinted` removes the class from the old cell, adds it to the new one, and re-renders both so the label follows (`play-page.ts:225-233`). `setCause` does the same. This is the "relabel pattern" of the spec: the cell that loses the marker is relabelled at once although its value did not change. Alternatives: derive the class from the DOM in `renderCell` (no state, but the marker would need the pressed cell anyway); or store the mark in `refreshHighlights` only (it is called from `showPuzzle` and `resetBoard`, which have no pressed cell). Chosen: state plus `refreshHighlights(changed?: [number, number])`, or a `setCause` called right after it; with no `changed` argument the marker is cleared. That makes "removed by every later board change that does not set it again" fall out of one call site rule: every board change calls the refresh, and only the click and the hint fill pass the cell.
3. **Order of calls matters in the click handler.** Today `onBoardClick` does `renderCell(r, c)` (296), `setHinted(null)` (297), `refreshHighlights()` (298), `updateWin()`. The new marker must be set after the highlights and the label of X must be rendered after the marker is known, so the order is: update the board, clear the old marker (relabel the old cell), `renderCell`, `setHinted(null)`, `refreshHighlights(X)`, which sets the new marker and relabels X. The hint fill has the same shape (`setHinted([h.row, h.col])` at 356 renders the cell first, then `refreshHighlights` at 357). `showPuzzle` sets `cause = null` next to `hinted = null` (307; its cell elements are replaced, so no relabel is needed); `resetBoard` (379-388) clears it with `setHinted(null)`; the capture mount (609-619) sets nothing, and `setHinted(capture.hinted)` keeps its meaning. The language re-render (`render()`, 589) calls `renderCell` for every cell, so the suffix is rebuilt in the new language with no extra code; the scenario «The marker follows a language switch» pins that.
4. **`cellLabel` takes a sixth positional boolean `cause` (`src/ui/strings.ts:29`, type 110, English 160).** It follows `hinted` and the file's shape ("same functions, same shape" of «English page text», which gains the exception). Alternatives: an options object (changes every call site and the parity test's sample calls for no gain) or a default `cause = false` (the 5-argument calls would compile, and a forgotten sixth argument at the one real call site would go unnoticed). A given cell wins over the other flags (`given ? ', задано' : (hinted ? ', підказка' : '') + (cause ? ', спричиняє порушення' : '')`); the code already orders given first. The five direct calls in `tests/play-page-english-text.test.ts` (208-210, 233-235) pass `false` explicitly.
5. **The mark: an `::after` triangle drawn with the six border longhands, not a background image and not the shorthands.** Borders survive forced-colours mode, where background images are dropped (the design reviewer checked it in Chrome's emulation). The longhands are not a style choice: a spike on 2026-10-11 parsed `src/ui/style.css`-style text with the project's jsdom (29.1.1) and the shorthand `border-left: max(0.5rem, 3px) solid transparent` was dropped silently from the rule's declarations (only the longhand form is read), so the stylesheet test could not see a shorthand with `max()`; the design file keeps its shorthands (it is not parsed by a test). The legs are `max(0.5rem, calc(((100cqi - (var(--n) - 1) * var(--board-gap)) / var(--n) - 4px) / 4))`: one quarter of the cell's inner width, and the floor of `0.5rem`. The variables exist in the product (`--n` and `--board-gap` on `.board`, 201-248; `container-type: inline-size` at 212, like `--cell-font` at 272). `position: relative` goes on `.cell-cause` and not on `.cell`; `.cell:focus-visible` (347) already declares it, so the scenario says "only `.cell-cause` and `.cell:focus-visible`" and does not claim uniqueness. `pointer-events: none` keeps clicks on the cell. `.cell-violation` already uses `border-width` and `border-color` longhands (319-335), so a hinted cause keeps its dashed 2px border and no change to that rule is needed. Trade-off: the mark is only as exact as the CSS expression: a test cannot compute the pseudo-element in jsdom, so the unit test pins the declared text and the e2e test reads real pixels in two cases (decision 8).
6. **The forced-colours rule and the colour scans (the user's decision: adopt).** The rule, scoped inside `@media (forced-colors: active)`: `.cell-cause::after { forced-color-adjust: none; border-top-color: ButtonText; border-left-color: transparent; }`. How the existing scans in `tests/helpers/css.ts` treat it, checked on 2026-10-11:
   - `COLOUR_LITERAL` (270) does not match `ButtonText`; `NAMED_COLOURS` (273-289) holds the CSS Color 4 named colours and no system colour, so `namedColoursIn` returns nothing; `transparent` is an allowed keyword (292).
   - The properties the scan reads (`COLOUR_PROPERTIES`, 305) are `color`, `background-color`, `border-color` and `outline-color`; `border-top-color` and `border-left-color` are not among them, and the shorthand clause (`SHORTHANDS`) does not list them either. So all existing scans pass on the rule as it is.
   - That is a gap of the helper, not an endorsement: FR-65 says every colour a rule uses is a token, and `ButtonText` is not one. The spec makes the exception deliberate and narrow: exactly one declaration outside `:root` may hold a system colour, `border-top-color: ButtonText` of `.cell-cause::after` inside `@media (forced-colors: active)`, pinned by a **new** scan (the CSS Color 4 system colours, case-insensitive; the CSSOM serialises the keyword in lower case). No existing scan is changed or loosened. Alternative considered and not taken: extend `COLOUR_PROPERTIES` to the per-side longhands so the old scan sees `buttontext` and add a whitelist; that changes a scan that guards every token, for a one-rule case (open question 1, alternative).
   - **FR-65 is signed text and does not name the exception.** The user adopted the forced-colours rule on 2026-10-11 (REVIEW.md, the answers at the end), but that question was about the rule, not about FR-65's "every colour a rule uses is a `var(--color-...)` token". So the exception needs a recorded clause in FR-65 before the folder is audited (tasks 1.1; open question 1). Proposed clause, appended to the sentence that ends "… and no colour literal appears outside these blocks": «One exception: the system colour keyword `ButtonText` as the `border-top-color` of the cause mark inside `@media (forced-colors: active)` (the user's adoption of the forced-colours rule, 2026-10-11).»
   - **How a test must read the selector.** `declarationsFor(parsed, '.cell-cause::after')` merges every rule of that selector, a later declaration winning (`tests/helpers/css.ts:248`), and the forced-colours rule is later in the file, so it would return `buttontext` for `border-top-color`. A test of the token binding filters `rulesWithSelector` by an empty `context` (the top-level rule) and reads that one; a test of the forced-colours block filters by the context `@media (forced-colors: active)`. The spec scenarios say "the top-level rule (outside any at-rule)" for this reason.
   - Not ADR-worthy now. It becomes one if a second system colour or a second forced-colours rule is added.
   - The product's `src/ui/style.css` gets the block in the port (task 5); the design's file gets it first (task 2), so the freezes are made from the final design.
7. **The design mirror and the refreeze are provenance-only, in a fixed order.** `designCommit` is `git log -1 --format=%H -- design/v0` (`scripts/freeze-design-paint.mjs:334`, `freeze-design-geometry.mjs:115`); the design touch is not committed yet. So: add the forced-colours block to `design/v0/app/binarka.css`; the parent commits `design/v0` (the touch and the mirror); `pnpm build` in `design/v0` (the `/cause*/` routes add files, so `designBuildSha1` changes: that is provenance); run both freeze scripts; the diff of the two JSON files may show `designCommit`, `designCssSha1` and `designBuildSha1` and nothing else. The design's `.cell-violation` changed from the shorthand `border: 2px solid` to `border-width` and `border-color`: the computed paint is the same for every cell kind of the ten sampled cases (none is a hinted violating cell), and the 170 reference shots are byte-identical (REVIEW.md, checked twice). If any other field changes, stop and report: it means the design touch moved a sampled paint. «The main column takes the design palette» is therefore not modified.
8. **The browser check reads two corner pixels (declared-method-needs-mechanism; sampling-blindness).** FR-120 forbids a mark at mount, so the e2e test makes it by a click on a capture board (FR-119) built on the design fixture's givens: two adjacent entered 0s and an empty non-given cell beside them. It reads the pixel 4 CSS px inside the top-right corner of that cell's border box before the press (must not be the border colour: the closed-pixel guard of the backdrop test), clicks, and reads again (must be `--color-violation-border` within 1 per channel), and reads the same pixel of the violating neighbour (must not be). Four px is inside the triangle for any leg of 8px or more (2px of border, so 2px from the padding corner on each axis: 2 + 2 = 4 ≤ 8). It also clears the cell's rounded corner: `.cell` has `border-radius: var(--radius-s)`, `--radius-s: 0.375rem` = 6px (`style.css:102, 289`), and the diagonal point 4px in from the outer corner is at distance (r − 4)·√2 = 2.83px from the arc's centre, inside the inner arc of radius r − 2 = 4px, so the neighbour's same pixel is fill or stripe and never its 2px border (the condition is (r − 4)·√2 ≤ r − 2, true for r up to about 8.8px). If the radius token ever grows past that, the negative control moves to a pixel 4px below the top edge at the cell's horizontal centre (fill or stripe, never border) and the neighbour read stays as a secondary assertion. Cases: light at 6×6 at 1024×768 and dark at 8×8 at 375×812 (the second reaches the leg's floor and the dark pair). Coverage is `sampled`: it says nothing about 320px, landscape (844×390, where the floor binds), 4×4 or the other theme at the other size. Escalation: the design stills (`docs/design/cause-touch-2026-10-11/`, reviewed by a design-reviewer) and a width sweep in the smoke test reading the pseudo-element's `border-top-width` (>= 8px at every width). The file is `e2e/nfr-14-cause-mark.spec.ts` so that the existing `layout` project's `testMatch` (`nfr-14-*`) picks it up and `playwright.config.ts` stays untouched (open question 4). `getComputedStyle(cell, '::after')` is a secondary assertion if a spike shows it readable, never the only one.
9. **Three MODIFIED requirements beyond the draft's §5 list, each one token or one row.** «English page text» has the table of English texts (the row of the cell labels gains the suffix, marked as proposed wording), says `strings.ts` keeps its shapes (`cellLabel` gains an argument, which is a shape change, so the sentence needs its exception), and its parity scenario gains a sample with a cause. «Page text is per mode» (scenario regex, `tests/play-page-english-text.test.ts:140-141`) and «Ukrainian page text» (scenario regex at baseline line 547) enumerate the cell-name grammar: no scenario board has a cause, so they stay true, but «Cell labels» now defines a longer grammar and an auditor would flag the contradiction. If the user prefers the draft's list, those two edits can be dropped without touching anything else (open question 3).
10. **A hint fill is a remover only on paper.** FR-120 lists "a hint fill" among the actions that remove the marker. A marker exists only while the board breaks a rule, and the hint refuses such a board (`src/engine/hint.ts:34`, FR-26), so no hint fill can follow a marker. The spec says so, and the scenario «A hint cannot follow a marker» pins the refusal instead of a removal that cannot be tested. The one way a hint sets the marker is P6 (a fill that breaks a rule, reachable with inconsistent givens in tests).
11. **The `snapshot()` sweep is a classification, not a rewrite.** `snapshot()` (`tests/helpers/play-page.ts:546-556`) includes each cell's class list. A before/after comparison across an action that changes no cell (a panel, a theme, a language, a refused hint) cannot change, because the marker is kept; those are most of the 83 calls in 18 test files (the draft's 84 counted the definition too) and must stay equal. A comparison that spans a press creating a violation can change: it is listed and changed only where FR-120 demands it. The test-engineer lists every comparison with its class (kept equal / changes because a press makes a marker) in `docs/qa/add-violation-cause/red-run.txt`; a comparison that fails for any other reason is a finding.
12. **The English suffix is proposed wording (FR-111; the TD-Q2 precedent).** ", causes a violation" is a proposal. Task 4.1 puts it to the user before the port, with the default as proposed; the Ukrainian «, спричиняє порушення» is signed (CQ-5).

## Data model

- **Page state** (in `mountPlayPage`'s closure, not stored): `cause: [number, number] | null` next to `hinted`; at most one cell; set by the click and the hint fill; null after `showPuzzle` and `resetBoard`.
- **Class and label of a cell** (what the DOM shows):

| Cell | `cell-cause` | Suffix (Ukrainian / English, proposed) |
|---|---|---|
| given | never | «, задано» / ", given" |
| hinted, not cause | no | «, підказка» / ", hinted" |
| cause, not hinted | yes | «, спричиняє порушення» / ", causes a violation" |
| hinted and cause | yes | «, підказка, спричиняє порушення» / ", hinted, causes a violation" |
| any other | no | none |

- **Contrast** (WCAG 2 from the A-57 literals; recomputed 2026-10-11): `--color-violation-border` against the violation fill 5.38 (light) / 6.24 (dark); against the stripe 4.33 / 4.61; against the hover ring 2.45 / 2.00 (accepted adjacency, not a pair). No token is added: the 27 stay; `CONTRAST_PAIRS` gains one pair (group `cause-cue`), 35 in all.

## Error handling strategy

- The page has no runtime error path for this change: the marker is computed from a pure function on a board the page already holds. A failed generation keeps the board and so the marker (FR-88); a cancelled confirmation changes nothing.
- A wrong marker surfaces as a failing assertion that names the cell: the oracle sweep compares the class set to `findViolations` after each press at N = 4, 6 and 8, with a non-vacuity count (at least one press with and one without a marker per size).
- The stylesheet test names the rule and the declaration. The new system-colour scan reports `selector { property: value }` like the others.
- e2e: one message per case; a closed pixel (before the press) that equals the border colour is a failure of the case, never a skip. An unstable capture is a harness defect to file, not a finding (AGENTS.md: capture determinism). Before any capture, `lsof -nP -iTCP:4173 -sTCP:LISTEN`, `4174`, `4176` and `4177` show no orphaned `vite preview` of this worktree; after Playwright runs `docs/qa/e2e-report.json` is restored (`git checkout docs/qa/e2e-report.json`).
- A failure outside the new files (an old test that now fails) is a finding. It is not a licence to edit that test unless a delta of this folder demands it.

## Risks and mitigations

- **A snapshot comparison breaks for a reason other than FR-120.** Mitigation: the classification of decision 11, in the red run.
- **The label grammar is pinned in more places than listed.** Mitigation: the sweep (tasks 3.4) greps `tests/` and `e2e/` for `, підказка`, `, hinted`, `задано|`, `aria-label` reads after a click; a hit whose state yields a cause is changed and listed with its source.
- **The mark is hard to see at 8×8 on a 320px phone in light** (the design review: findable "after a short scan"). Mitigation: none in this slice; the user kept the signed size; the floor of 8px is the guarantee, and the smoke test records what the mark looks like there.
- **The design freezes move more than provenance.** Mitigation: the diff gate of task 2.4 stops the slice.
- **A second `forced-colors` rule or system colour appears later.** Mitigation: the new scan counts exactly one; a later rule changes the scenario by its own delta.
- **`position: relative` on `.cell-cause` changes stacking with the hover ring or the focus outline.** Mitigation: `.cell:focus-visible` already sets it with `z-index: 1`; the outline is outside the cell; the hover ring is an inset shadow painted under the mark's legs (accepted, CQ-7).
- **The English wording is changed by the user after the tests are written.** Mitigation: gate 4.1 precedes the port, and the wording lives in one constant (`EN_CELL`).

## Open questions

1. **FR-65 and the system-colour exception** (decision 6). The spec carries the exception (`ButtonText` in the forced-colours block, pinned by a new scan), but `docs/requirements.md` FR-65 does not name it, and the user's adoption of the rule is not a waiver of FR-65's text. Default: the parent puts one line to the user and, on the user's yes, adds the proposed clause to FR-65 with an autonomy-log row **before** the folder audit (tasks 1.1), so the auditor reads the amended text. Alternative: drop the exception from the spec and keep the forced-colours rule as a note in the stylesheet (the user's answer said adopt, so this is the less likely path). Further alternative, not recommended: extend `COLOUR_PROPERTIES` to the per-side longhands now.
2. **The English suffix** (decision 12). Default: ", causes a violation" (task 4.1 asks).
3. **The three edits beyond the draft's §5** (decision 9). Default: keep them; dropping «Page text is per mode» and «Ukrainian page text» changes only the regex scenarios, and dropping «English page text» is not possible (the table needs its row and `cellLabel` its sixth argument).
4. **The e2e file name.** Default: `e2e/nfr-14-cause-mark.spec.ts` (no config edit). Alternative: `e2e/fr-120-cause-mark.spec.ts` with one more `testMatch` pattern, which needs the user's approval as in autonomy-log rows 117 and 150.
5. **The sampled sizes of the e2e check.** Default: light 6×6 at 1024×768 and dark 8×8 at 375×812. Alternative: all of 4, 6, 8 in both themes (12 cases), at more cost.
