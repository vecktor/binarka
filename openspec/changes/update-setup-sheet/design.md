# Design: update-setup-sheet

## Context

G2 block B of the parallel plan (`docs/handoff/parallel-g2-plan-2026-10-11.md`), implemented by its own session in its own worktree, started from a `main` that already holds the merged `update-panel-shell`. The signed text is FR-65 (the ring clause), FR-96, FR-99, NFR-12 to NFR-14, A-57 (appendix) and A-60 in `docs/requirements.md` and `docs/handoff/setup-sheet-amendment-draft-2026-10-11.md` (SQ-1 A, SQ-2, SQ-3 A, SQ-4, SQ-5, SQ-6, XQ-1 A; autonomy-log row 172).

Today (`src/ui/style.css`, before the shell): `.setup-sheet` is a bottom sheet up to `80dvh`; from 48rem a 28rem panel centred with `margin: auto`; it keeps `line-height: normal` and a 24px padding; the cards take the base `button` padding (`10px 16px`) and a `--color-control-border` border; the checked card and size option are `--color-focus` on `--color-given-bg` with an inset-shadow dot; «Почати» is outlined. The design (`design/v0/app/binarka.css`, `review-set-14`) has the three regimes, the indent, the `--color-primary` paint and a filled «Почати».

## Goals

- The sheet has the design's size, place and paint in the three regimes, light and dark, and ends at least 0.5rem below the button row from 48rem.
- At the six sampled viewports no edge of the sheet cuts the idle line; the cut line at 1366×650 is gone.
- Every setup shot of the gate rises against run 9.
- The stylesheet stays inside the colour scan and the shell's tests stay green without an edit.

## Non-goals

- Motion (SQ-6), the theme and language options and the settings panel, the dialog, the shell's tokens, a pixel floor, Safari and Firefox.
- No edit to `design/v0`, to the locked adapter `scripts/check-visual-parity-adapters.mjs`, to `playwright.config.ts`, to `src/ui/play-page.ts` or to a requirement other than the nine named in `proposal.md`.

## Decisions

1. **The deltas are written against the post-shell text.** The MODIFIED blocks of «Borders, cues and focus rings have enough contrast» and «Main column layout geometry follows the design reference» reproduce the shell's blocks (`openspec/changes/archive/2026-10-11-update-panel-shell/specs/play-page/spec.md`) with only B's edits; the shell's ADDED «The panels take the shared surface paint» is reproduced with one scenario edited. If the shell's text changes before it is archived, the implementing session re-reads this folder (task 1.1). Trade-off: B depends on a text that is not yet baseline; the cost of waiting for the shell is zero (B starts after its merge).
2. **Three media blocks, one `.setup-sheet` rule in each.** Phone in the base rule (`max-height` twice, `90vh` then `88dvh`), 22.5rem in its own block, which comes after the base rule (`src/ui/style.css` ~798; for example in the 22.5rem block at ~1029), because the shell test `tests/play-page-panel-shell-stylesheet.test.ts:44-48` reads the first `.setup-sheet {` block of the file as the top-level one; `.setup-close` keeps exactly one top-level rule (that test, :139-141), so its padding and border go into that rule; the full cover in the one rule inside `@media (min-width: 48rem)`, the anchored regime in `@media (min-width: 48rem) and (min-height: 44rem)` after it. The shell's stylesheet tests read "the rule" `.setup-sheet` outside any at-rule and inside `@media (min-width: 48rem)` (its `box-shadow`, `border-color`, `background-color`), so B merges its 48rem declarations into the shell's rule, redeclares none of the shell's three, and puts none of them in the anchored block. The design writes the 48rem `min-height` as a second `.setup` rule and restates `max-height` after an unconditional rule (`binarka.css` 1049-1060); the page needs neither. If a shell test still fails, it is a finding for the user, not a test to edit. Source order decides the anchored regime over the full cover (equal specificity).
3. **The floor reads the board side through the root.** `min-height: min(calc(100dvh - 7rem), calc(min(var(--board-width), var(--column)) + 8.5rem))` and `... - 10.75rem ... + 4.75rem` are the design's formulas, copied as they are: the shell moved `--board-width` to `#app` keyed on `data-size`, so the sheet, inside the root, reads the board's value, also for a 4×4 board (B smaller than the column). No `:has(`. The constants come from the design's own comments (`binarka.css` 1000-1007, 1010-1016): the summary ends at 9.25rem; the anchored sheet starts 0.5rem below it (9.75rem); the button row ends at `B + 14rem`; so `B + 4.75rem` from 9.75rem ends at `B + 14.5rem`, 0.5rem below the row; the full cover starts at 6rem, so `B + 8.5rem` ends at the same line. The `max-height` ends the sheet 1rem above the window's bottom in both regimes, so "or at the window's limit" is `H - 16`.
4. **The design's inner metrics are part of the requirement, and the page's base `button` rule is not the design's** (the coordinator's note from the audit of block A). The page's `button { font: inherit; padding: 10px 16px; border-width: 1px; border-radius: 6px }` gives every control of the sheet a padding the design does not have: the design's buttons get the browser default and their `min-height` wins. Checked control by control against the design: the size options keep `0 0.5rem` (the page already says `0 8px`); the level cards need `0.5rem 0.75rem` (`0.375rem 0.625rem` at 22.5rem), today the page's rule states no padding and the base `10px 16px` applies; «Почати» needs `0 0.75rem` and «Закрити» `0 0.5rem` (the design's `.setup-start` and `.setup > .setup-close`), today both inherit `10px 16px`; the size control loses the page's `max-width: 22rem`, `margin: 0 auto 12px` and 8px radius (the design: `width: 100%`, `0.625rem`, the gap below comes from the level group's `margin-top: 0.75rem`); the sheet's own padding is `1.5rem 1rem calc(1rem + safe-area)` (`1rem` bottom from 48rem, and `padding-top: 1rem` at 22.5rem and narrower, `binarka.css` 931-936), not `20px 16px 16px` and `24px`; the unchecked size option is `--color-text-muted` at weight 500 on the control fill (the design's `--ink-muted` on a transparent button; `transparent` is not a token and «The size buttons set their own colours…» needs one). These decide the sheet's height (it is `fit-content` between the floor and the cap) and the description's left edge, which the e2e compares at 0.5 px. Type metrics: the name `1rem/1.25/700`, the description `0.875rem/1.35/400` (the page has no `.level-text` rule: it inherits `1rem` and `1.5`), the reason line `0.875rem/1.35`. Trade-off: more declarations than the amendment's list; without them the geometry cannot pass. They are `.setup-sheet*`, `.level-control*`, `.size-control`, `.setup-start`, `.setup-close` and the reason line only, B's share. See open point 1.
5. **`--color-option-border` is decoration (SQ-1 A), pinned by a negative test.** 1.98 / 2.06 against the card, 1.98 / 1.90 against the sheet. The spec scenario records the ratios and asserts no pair names the token, so the exception is visible and cannot widen silently. The ring's three pairs replace it as the pinned cues. Not ADR-worthy by itself (A-60 records the reasoning, citing WCAG 1.4.11's Understanding note); an ADR would be proposed only if a second component takes the same exception.
6. **The dot is a `background-image` longhand.** The design writes `background: radial-gradient(circle, var(--primary) 0 40%, var(--surface) 45%)`; the page writes `background-color: var(--color-control-bg)` on the ring and `background-image: radial-gradient(circle, var(--color-primary) 0 40%, var(--color-control-bg) 45%)` on the checked ring, so the colour scan's longhand clause (`background-color` is one `var()`) keeps applying to the ring. No `box-shadow` on any ring (SQ-2, SQ-3 A). The scenario «The checked level has a cue besides colour» now requires the gradient and forbids `inset`; the signed text says "accepts … instead of the inset", read as a replacement because the added requirement pins the gradient and a scenario that accepted both would leave the cue unpinned.
7. **The ring pairs go to existing groups.** `control-border` on `control-bg` joins group `control-border`; the two primary pairs join `hinted-cue` ("the hinted cue and the primary colour"). No new `PairGroup`, so the helper types and `contrastProblems(set, groups)` calls (`tests/play-page-palette-stylesheet.test.ts:118`, `tests/play-page-stylesheet.test.ts:247`) cover them with no edit.
8. **The 28px margin stays (SQ-5), with its proof.** The design's rule is unconditional: 24px at every width (`binarka.css` 600-602, restated at 48rem), 1rem at 22.5rem and narrower (A-60 says so since its correction at autonomy-log row 173); with them the ring of the last option sits under the footer strip (`docs/qa/update-page-layout-geometry/nfr-13-red-after-port.txt`). The scenario names the rule and the e2e of «Cells and buttons show a visible, unobscured focus indicator» (four viewports) as the proof. The design's bottom padding is 16px, so the page's 24px "up to" bound and the `calc(2.75rem + 48px)` value stay true and need no edit of that requirement or of `tests/play-page-stylesheet.test.ts:320-326`.
9. **The geometry cases go under their own key, `setupSheet`.** `e2e/nfr-14-layout-geometry.spec.ts:49` pins `fixture.cases` to the 32 shots, and block A already uses `rulesPanel`. The key holds `selectors` (`[data-section="setup"]` and `[data-section="setup"] [data-control="level"] button:first-of-type .level-text`), `coverage: "sampled"`, its own provenance and 12 cases: `<w>-light-setup` (the 6×6 fixture) and `<w>-light-setup-four` (the 4×4 fixture, which exercises B) at 320, 375, 768, 1024, 1366 and 1440. The design's `/setup/` and `/setup-four/` routes are open at load (a press would close them); the page side replays the recorded `afterLoad: "open-setup"` (press the summary button, wait for `:popover-open`) with the capture board of the case. The existing 32 cases and the existing provenance fields `designCommit` and `designCssSha1` come out unchanged; `designBuildSha1` differs between worktrees and is recorded under the new key's own provenance (the coordinator's note from block A's audit). Only the left edge of the description is compared, not its box. **Each case records two boxes of the sheet: the design's own (`boxes`) and the expected product box (`expected`).** The 28px margin (decision 8) makes the sheet 4px taller than the design's (12px at 320, where the design has 1rem; never past the cap, so 2.31px at 320×700 in the 6×6 state) wherever its content, not the `min-height` floor or the `max-height` cap, decides the height: at 375×812 and 320×700 (88dvh and `100dvh - 9rem` are far above the content), and probably in the `four` states from 48rem (the reason line adds height while B and so the floor shrink). Comparing the page with the unmodified design would make the box test unsatisfiable without breaking the signed departure or loosening the tolerance. So the freeze script captures each case twice: once as the design is, and once with one rule injected into the design page in the browser, `.setup .level-control { margin-bottom: 28px }` appended after the design's stylesheet (nothing is written to `design/v0` or to `src/ui/style.css`, so no scan of the page is touched). The key records the deviation (rule, design value, product value, reason A-60/SQ-5) the way «The main column takes the design palette» records the A-57 deviations: the test compares to `expected`, prints `boxes` beside it on a miss, and asserts the deviation is recorded. Cases where the floor or the cap decides come out identical. The script guards the injection like `e2e/nfr-14-palette.spec.ts:183` guards its deviations: it reads the design's computed `margin-bottom` of the level group before injecting and fails unless it is 24px (16px at 22.5rem and narrower). Each case also records, as block A's `rulesPanel` does, `layout` (the design sheet's `scrollHeight`, `clientHeight`, resolved `min-height` and `max-height`, and `decidedBy`: `min-height`, `max-height` or `content`), and the deviation lists the cases that `content` decides. The design's DOM carries the selectors (`binarka-page.tsx` 373-407: `data-section="setup"`, `data-control="level"`, the buttons, `.level-text`).
10. **The floor and the no-cut checks are separate from the box match.** The box match compares to the design; the floor check (from 48rem: `S.bottom >= min(R + 8, H - 16) - 0.5`) and the no-cut check (all six viewports: no edge of the sheet strictly inside the idle line's ink band; the box was the first reading, but the design's own sheet ends 0.8 px inside the line's box at 1024×768 and the page 4.8 px with the 28px departure, while the glyphs stay clear, so on 2026-10-11 the user chose the ink: first line's top + `fontBoundingBoxAscent` − `actualBoundingBoxAscent` to last line's top + `fontBoundingBoxAscent` + `actualBoundingBoxDescent`, `docs/qa/update-setup-sheet/green-run.txt`, open finding 1) read the page alone, so a regression in the design's formula cannot hide in both. A phone viewport that cuts the line is a finding, not a licence to loosen the check. A fine-step sweep (`SETUP_SHEET_SWEEP=1`, 16 px steps) is the stricter instrument named, never a continuum claim.
11. **Selectors stay.** `tests/play-page-level-stylesheet.test.ts` reads `.level-control button`, `[aria-checked='true']`, `[aria-disabled='true']`, `.level-control button .level-name::before` and `.size-control button[aria-checked='true']`. The port keeps those selectors; the reason line is found by matching the element (`[data-level-reason]`), so its selector may change.

## Error handling strategy

- The page has no new runtime error path: the change is stylesheet-only. A wrong token, a stray old binding or a media block out of order is a stylesheet test failure that names the rule and the declaration.
- The e2e fails (never skips) with the case, the element and both boxes on any difference; it asserts the sheet is `:popover-open` before it reads, and fails with the freeze instruction if the key `setupSheet` is absent. The freeze script fails with the build instruction of `design/README.md` when `design/v0/out/index.html` is missing.
- A capture-unstable run is a harness defect to file, not a pixel finding (AGENTS.md, capture determinism). Captures take the lock of task 0.2.

## Risks and mitigations

- **The nfr-13 premise may fail at 1366×650, and at 320×700 and 320×568.** At 320 the design's `padding-top: 1rem` and tighter cards shorten the content by about 8px plus the card tightening, against a `100dvh - 9rem` cap (556px at 320×700, 424px at 320×568); the premise is re-checked at both before the port is called green. With the design's metrics and a 538px sheet (`650 - 7rem`) the contents with «Поле 4×4» marked (padding, size control, the reason line, four cards, the 28px margin, the footer) are about 500-520px and may no longer scroll, so the premise of the focus walk ("the sheet scrolls") fails there. The test asserts the premise on purpose. Mitigation: smoke and red/green runs read the premise first; if it fails, stop and put it to the user (the scenario, not the premise assertion, would change); nothing is loosened. Outcome (2026-10-11): the premise held at 1366×650, 320×700 and 320×568 and failed at 375×667 (573 = 573); the user moved the 375-wide case to 375×600 (a ninth MODIFIED requirement).
- **The sheet's height differs from the design's by the 28px margin in the content-decided cases** (a certainty, not a risk; decision 9 records it as an expected box). Any other difference (type metrics, safe-area) is a defect: decision 4; the 12 cases compare the box with `expected` at 0.5 px; `visual-block --block setup` localises a residual. The pixel gate compares with the unmodified design, so the 4px (12px at 320) sit in every content-decided setup shot's residual; the run-vs-previous explanation names them.
- **The idle line is cut at a phone viewport.** Mitigation: the no-cut check runs at all six viewports; a failure is a finding.
- **The shell's tests fail on the merged rule** (decision 2). Mitigation: merge declarations; report, never edit the shell's tests (two of them, "exactly three pairs", are edited on purpose, by the delta that demands it).
- **Dark bands.** Controls inside the sheet stay `#24201b` on the sheet's `#2c2620`, as the design's own `--surface` controls do. Not a defect.
- **Safari and Firefox are untested** (NFR-7); `dvh` and the popover top layer may differ there.
- **A setup shot falls:** the block stops and explains it.
