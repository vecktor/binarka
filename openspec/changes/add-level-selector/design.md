# Design: add-level-selector

**BLOCKED until DL1 `add-difficulty-engine` is archived and a new design set `design/v0-screenshots/review-set-6/` (with updated `design/v0/` sources) exists AND the user has said in chat that the reference moves to it (Q3; `review-set-5` is frozen).** See `proposal.md` and `tasks.md` 1.1 and 1.2. The interface of DL1 used below (`generate(size, seed, level)`, the hint without a ceiling, a distinct run-out error) is taken from `docs/requirements.md` (FR-13, FR-77, FR-81, FR-84) and must be re-read from DL1's archived `puzzle-engine/spec.md` before tests are written (task 1.3).

## Goals

- The level control, the description line, the 4×4 behaviour, the confirmation of a level change, the size and level interplay and the techniques section of the rules panel (FR-44, FR-87 to FR-94, with the amended FR-42, FR-57, FR-58, FR-67, FR-68, FR-73).
- NFR-4, NFR-5 and NFR-9 hold for every new text and for the new radiogroup.
- All new text in `src/ui/strings.ts`; no new colour token; no new dependency; no storage (TC-12).

## Non-goals

- Layout, wrapping at 320 px, 44 px targets, the one-screen fit and the pixel match: held NFR-10, NFR-12, NFR-13, NFR-14. jsdom has no layout (TC-13), so this slice pins DOM, attributes and stylesheet declarations only and claims nothing visual.
- Arrow-key navigation of the radiogroups (A-24, FR-59), remembering the level (TC-12), a visible error when generation fails (A-38), decorative examples for the techniques items.
- Engine work, the CLI, FR-74 to FR-86 and NFR-16, NFR-17 (DL1). The hint sentences FR-78 to FR-80 are displayed, never restated.
- Authentication: none exists, so no redirect-to-login or forbidden case applies (play-page Exclusions).

## Key decisions

1. **One `level` beside `size`; one generation path.** `newPuzzle(size, level)` becomes the only place that calls the seed source and `generate(size, seed, level)`; the mount, «Нова головоломка», a size change and a level change all go through it, so the "one seed per attempt" rule of the baseline stays true by construction. A failed attempt (a throw, a run-out, a wrong-size result) changes neither `size` nor `level`. Trade-off: a third argument on the injected `generate` option (`PlayPageOptions.generate`), so old two-argument test generators keep working (extra arguments are ignored) but a spy that wants the level must record it. The spy helper keeps `calls` as `{ size, seed }` and records levels in a parallel array, so about 30 existing `toEqual` assertions stay green.
2. **The confirmation machinery is reused unchanged.** A level press calls `requestAction(() => { changeLevel(l); })`, the same pending-action slot as size, new puzzle and reset. The dialog, its focus on «Скасувати» and Escape handling do not change. Trade-off: none worth naming; a second dialog would duplicate FR-67.
3. **A size change to 4 forces level 1 inside the same puzzle (FR-92).** `changeSize(4)` calls `newPuzzle(4, 1)` once: one seed, one generator call, one confirmation. The alternative, two steps (set the level, then the size), would need a level-3 4×4 puzzle that does not exist (A-34) or two dialogs. The level is not restored on the way back to 6 or 8 (spec scenario «Going back from 4x4 keeps level 1»); restoring it would add remembered state for no requirement.
4. **Unavailable levels use `aria-disabled="true"`, not `disabled`, and not hiding (Q1 option a).** Same pattern as the given cells (FR-69): the button stays focusable and readable, a press is a no-op guarded in the click handler, and `aria-checked` stays false. Trade-off: the handler must check the flag itself; the gain is a stable layout and a screen-reader user can reach the button and read why it is off through the description line. Alternative (b) hiding the control is rejected by the user's default.
5. **The description line is plain text with no role and no id (A-39).** The baseline allows ids only for the popover and the dialog (three per mount, tests count them), so no `aria-describedby`. It shows the reason at 4×4 instead of the level 1 line, as FR-91 says literally (see ambiguity B). Trade-off: a screen-reader user hears the state from `aria-checked`, not from the line.
6. **The page hint passes ceiling 4 (FR-77, Q2).** The engine's `hint(board, ceiling = 1)` keeps the three basic rules by default (user decision, autonomy-log row 88, option B; DL1 does not change the page), so the page changes `hint(board)` to `hint(board, 4)` and uses all four techniques at every level. The delta has a scenario that the same board gives the same hint at every level, so a future "ceiling = shown level" change fails a test. Cost: a level-1 player can get a hint no level-1 puzzle needs; accepted by the user.
7. **The level control has its own class and its own stylesheet rules.** `.level-control button` (plain, `[aria-checked='true']`, `[aria-disabled='true']`) each set `color` and `background-color` from the existing 13 tokens, 4.5:1, no `opacity`. They are not merged into the `.size-control` selector list, because the existing stylesheet tests read the declarations of `.size-control button` by that exact selector. Trade-off: some duplicated declarations; G2 (the palette port) may share them later.
8. **Rules panel DOM (spec-made proxies).** The rules list is the panel's direct-child `ul`; the techniques section is `div[data-section="techniques"]` with an `h3` «Складніші прийоми» and its own `ul`, placed between the rules list and the close button; no ids (the three-ids rule), no decorative examples. FR-93 gives the texts, not the elements; the hook, the `h3` and the order are made by this spec so jsdom can decide pass or fail, and they follow the user's updated design if it differs (task 1.4).
9. **MODIFIED, not ADDED, for the four baseline requirements whose text is a closed list, states the call or lists the buttons.** A requirement is modified only where its list is closed ("until…", "at no other time", "the three size buttons"); open clauses are covered by ADDED scenarios. «Cells and buttons show a visible, unobscured focus indicator» lists "the three size buttons" and its scenario reads "the three `button[role=\"radio\"]`", so the four level buttons are added (FR-65 text unchanged, FR-87). «Grid size selector» says "the page assumes that `generate(n, seed)` returns an n×n puzzle" (the call gains the level and a size change to 4 sets level 1, FR-92). «Seed is chosen outside the engine…» lists the attempts that take a seed ("the mount, each performed press of the new puzzle button and each performed change to another size … at no other time"), and «Hint message stays…» lists what clears the message. A level change is a new entry in both lists; leaving them would make the baseline contradict the new behaviour. «Pressing the shown size changes nothing» keeps its name (the archive matches MODIFIED by header) although it now also covers the level. The FR texts of FR-43, FR-51 and FR-40 do not change. «Hinted cell marker», «Highlighting follows every board change» and «Cell labels» are left unmodified on purpose: their general clauses ("any later board change", "after every board change", "every change of the cell") already cover a level change, and the new requirements add the level scenarios for the marker (cleared when performed, kept on cancel and on failure).
10. **Strings are pinned and provisional (Q6).** The delta tables pin the FR-89, FR-91 and FR-93 wording. When the user changes a line in chat, `src/ui/strings.ts`, the delta tables, `docs/requirements.md` (FR-89, FR-91, FR-93) and the tests change in one step, with Q6 as the source; nothing is re-worded silently.

None of these is ADR-worthy: no dependency, no storage, no new module contract. The only cross-slice contract, the three-argument `generate`, is DL1's decision (ambiguity A).

## Data model

No stored state (TC-12). Page state in `mountPlayPage`: `size` (4, 6, 8) and `level` (1 to 4, start 1), next to `board`, `givens`, `hinted`, `pending`. Derived on every shown board: the `aria-checked` of the four level buttons, the `aria-disabled` of levels 2 to 4 (true exactly when `size === 4`), and the text of `[data-level-description]` (`LEVELS[level].description`, or the 4×4 reason when `size === 4`). `src/ui/strings.ts` gains: the group name, four level names, four description lines, the 4×4 reason, the techniques heading and three items, as `as const` data. New DOM: one radiogroup with four buttons, one description element, one techniques section in the panel; no id.

## Error handling strategy

- Generator throws (including DL1's run-out error), or returns a puzzle that is not n×n: caught in `newPuzzle`, which returns false; the caller then changes nothing (board, messages, `cell-hinted`, size, level, `aria-checked`, description). No retry (A-38), no uncaught error, no message text (ambiguity C). The seed was already taken for that attempt, as in the baseline.
- Unavailable level pressed at 4×4, the level already shown, a cancelled confirmation, Escape: no-ops with the same list of non-effects as FR-73 and FR-67.
- Every mutation here is a click on a fixed button; no free value, so no validation message is needed and no raw 500 can reach the user. No authentication, so no redirect cases.

## Risks and mitigations

- **DL1's interface differs** (argument order, error type, hint ceiling): task 1.3 reads DL1's archived spec first; the delta and this design are edited before any test is written.
- **Design reference changes the DOM** (heading level, order inside the panel, class names): task 1.4 compares; the spec-made proxies (decision 8) are the ones that move, not the FR texts.
- **A level-4 board is slow to generate on a click** (NFR-2, NFR-3 are DL1's, measured there); the page is synchronous, so a slow generation freezes the click. Mitigation: none in this slice; DL1's 50% margin is the control. Watch it in the browser check (4.9).
- **Run-outs on the page** (A-35, A-38): possible in principle with random page seeds; the player sees nothing happen. Mitigation: the previous board stays; a message is a later signed step (ambiguity C).
- **Strings change after tests are written:** decision 10; one step, one source.
- **The loose seed regex of «Seed is not shown»** could match digits in new text: the new texts contain "4×4" only; the scenario runs with the new controls present (tasks 2.1).
- **Panel gets long on a phone** (six items): layout is held NFR-14, observed in the browser check, not claimed.

## Ambiguities and assumptions (also reported to the orchestrator)

- **A. DL1 interface.** Assumed: `generate(size, seed, level)` with level last, `hint(board, ceiling = 1)` with the page passing 4, any thrown error is a generator failure for the page. Re-check at 1.3.
- **B. FR-91 reading.** The description line shows the reason and not the level 1 line at 4×4 (literal FR-91: "the description line shows …"). If the user wants both, FR-91 and the delta change deliberately.
- **C. Silent failure.** A failed level change shows no text (A-38 "the old board stays"). The quality bar asks for inline errors on mutations; none is specified here because there is no free input, but a player may not notice nothing happened. Left to the user.
- **D. FR-77 is owned by DL1.** The delta cites it in `Traces:` of «The page hint uses all four techniques» and a test here carries `@trace FR-77`; DL1's tests carry it too.
- **E. Q6 includes FR-78 to FR-80.** The three hint sentences live in `src/engine`; if the user changes them in chat during this slice the engine strings and DL1's pinned tests change deliberately here.
- **F. Spec-made names.** `div[data-section="techniques"]`, the `h3`, the `level-control` class, the selectors `.level-control button[...]`, the order inside the panel, and the requirement name «Only the first level exists at 4x4» are not in the FRs; they are confirmed against `review-set-6` before tests pin them (task 1.4).
- **G. NFR-4 on page text.** The signed NFR-4 covers hint sentences only; the one-sentence check on the description lines, the 4×4 reason and the techniques items is spec-made, by analogy with NFR-4 (the plan, section 4.10, lists NFR-4 as travelling with DL2).
- **H. Stylesheet requirements for the level buttons** (4.5:1 for all three states, no `opacity`, the own `.level-control` rules) are spec-made and stricter than NFR-9 and WCAG (which exempts inactive controls); the `aria-disabled` state is held to 4.5:1 so the reason stays readable.
