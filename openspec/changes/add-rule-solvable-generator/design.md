# Design: add-rule-solvable-generator

## Goals

- Every puzzle `generate(N, seed)` returns for N = 4, 6 and 8 is solvable from its givens by the hint engine's fill alone, in the order of A-7, ending on the solution (FR-27, A-5). A hint is therefore always available on a board whose entries agree with the solution and that still has an empty cell.
- The guarantee is by construction (A-31): a candidate puzzle is accepted only if the check passes, so it holds for every seed, not only the fixed seed set. It is tested over the fixed seed set (seeds 1 to 20 for each N).
- FR-14 (deterministic from the seed), FR-15 (exactly one solution) and NFR-1 to NFR-3 (200 ms, 500 ms, 3 s worst case over the fixed seed set) hold with their tests unchanged.
- The solution of every seed stays the same; only the givens change (decision 4).

## Non-goals

- Difficulty grading, a minimum or maximum number of givens, a "hardest puzzle" search (FR-44, Future). The generator still takes no difficulty parameter.
- Any rule beyond pair, sandwich and count (no X-wing, no look-ahead, no guessing). If the three rules cannot finish a puzzle, that puzzle is not generated.
- N = 10 to 16: accepted by size validation (FR-49) but not claimed, not tested and not timed (FR-18 Future).
- Changing the hint engine, its sentences or its order (FR-19 to FR-26, A-7). `src/engine/hint.ts` is read, not edited.
- Relaxing a timing bound or shrinking the seed set (decision 6).
- A page change. The page already shows the engine's hint; FR-25 (the no-rule sentence) stays for boards with player errors or entries that leave no rule applicable (A-5, A-6). No authentication exists, so no redirect-to-login or forbidden case applies.

## Key decisions

1. **Acceptance by construction in the carving loop (A-31).** Today `generate` fills a complete valid grid (`fillGrid`, randomised backtracking), shuffles the cell positions and removes each cell whose removal keeps exactly one solution under a node budget. The new rule: remove a cell only if the board is still solvable by repeated hint fills. The starting board (the full grid) is trivially rule-solvable, and every removal is re-checked with `solveByRules` before it is kept, so each accepted removal leaves a rule-solvable board by the check itself: the loop needs no retry and no failure path, and the final board is rule-solvable by induction on the accepted removals, with no monotonicity assumption. Separately, rule-solvable puzzles are closed upward: giving the player more cells (entries that agree with the solution) never removes a deduction, because the closure of the three rules only grows with the known cells, and the order of the fills does not change the final closure. That argument is not needed by carving; it justifies the partial-board scenario («A hint is always available on a correct partial board») and the maximality of the carving (a cell kept because its removal failed would also fail later, with fewer cells). Trade-off: the puzzle is a maximal carving under a stricter predicate, so it typically has more givens than today at N = 6 and 8; the given sets are not nested (the carving paths diverge once the stricter predicate keeps a cell the old one dropped), so N = 4 measured slightly fewer on average. Alternative rejected: generate as now and retry whole puzzles until one is rule-solvable. Measured on a scratch copy of the engine (not evidence, redone by the red run of task 1.4): 9 of 20 seeds at N = 4, 17 of 20 at N = 6 and 20 of 20 at N = 8 are not rule-solvable today, so retrying would burn the time budget at N = 8 for no gain.
2. **The check uses the hint engine's fill (A-31).** `solveByRules(board)` copies the board, calls `hint(board)`, writes the fill into the board, and repeats until no empty cell remains (solved) or a call returns no fill (stuck: `none` or `broken`). It returns `{ solved, steps }`. Using `hint` rather than a second implementation of the three rules means the guarantee is about the rules the player is shown, with the order of A-7, and the broken-board precedence of FR-26 never triggers on a correct path (the board stays a subset of a valid solution). Trade-off: each call re-scans the board (a few N^2 operations plus the rule check of FR-26), with at most N^2 calls per check and at most N^2 checks per puzzle; measured cost is small (decision 6). It is an internal module `src/engine/rule-solve.ts`, not exported from `src/engine/index.ts` (like `countSolutionsBudgeted`), imported by `generator.ts`. No cycle: `generator` imports `rule-solve`, which imports `hint`, which imports `rules`.
3. **Uniqueness is implied; the solver is dropped from the carving loop.** Every fill of the three rules is forced: the value holds in every valid completion of the board. The solution is a valid completion of the givens, so every fill agrees with it, and a run that ends on a full board ends on the solution; every completion of the givens then equals it. So a rule-solvable puzzle has exactly one solution (FR-15), and the budgeted solver call (`countSolutionsBudgeted`, `CARVE_NODE_BUDGET`) is no longer needed in `generate`; the import and the constant are removed (lint would flag them). FR-15 is not weakened: its tests (`tests/generator-unique.test.ts`) still check every puzzle with the engine solver and with the independent oracle, 60 puzzles. Alternative rejected: keep the solver as an extra conjunct. It adds cost and a second way for the node budget to run out (a kept cell that the budgeted old rule would not keep changes the output for no gain); the soundness argument above makes it redundant. This is a judgement call that the review-gate should confirm.
4. **Determinism and unchanged solutions.** The fill phase stays first and consumes the same random draws, then the same `shuffle` of the positions; the new carving consumes no random numbers. So `solution` for each (N, seed) is identical to today (checked on a scratch copy over the 60 seeds of the fixed set), and every fixture that depends on a solution keeps working: `SOLUTION_8_TEXT` in `tests/helpers/play-page.ts` is asserted equal to `generate(8, 1).solution` in `tests/play-page-helpers.test.ts`. Risk: any random draw inserted before the fill, or any change of the shuffle, changes it (task 2.3 keeps the order). Same-seed same-puzzle (FR-14) holds because `hint` is deterministic and there is no `Math.random`, `Date` or `performance.now` in the engine (the node budget of the fill phase stays a count of work, not of time).
5. **No ADR now.** The decision adds no dependency, no storage and no contract between modules; it is the amendment A-31 applied. It becomes ADR-worthy only if the stop condition fires and a different generation strategy (for example a different carving order, or a rule-aware construction) has to be chosen.
6. **Stop condition (A-31), explicit.** The slice stops and an amendment is raised if, after the implementation of this design, any of `tests/generator-timing.test.ts` fails (200 ms at N = 4, 500 ms at N = 6, 3 s at N = 8, worst case over seeds 1 to 20), or the FR-27 test cannot be made to pass at N = 8 within the 3 s bound. Then: do not edit the bound, do not shrink the seed set, do not drop N = 8 from FR-27, do not accept a puzzle that fails the check, do not replace the hint loop by a faster function that was not agreed (a speed-up that changes how the check works is itself an amendment of A-31); stop, save the failing output to `docs/qa/add-rule-solvable-generator-red-run.txt` next to the red run, and tell the user. A soft tripwire: if the measured worst case at any N is over 50% of its bound, record it and tell the user before archive, because the bounds are measured on shared CI machines and may need margin (A-13). Expected margin, from a scratch measurement on the dev machine on 2026-10-06 (not evidence; the real numbers come from task 2.5): worst case 1.3 ms at N = 4, 8.1 ms at N = 6, 16 ms at N = 8.
7. **Test design.** The FR-27 test runs its own loop with the public `hint` (not `solveByRules`), so the test does not share the generator's helper. `solveByRules` has its own unit tests on hand boards. The test is red against today's generator because 46 of the 60 puzzles are not rule-solvable. The fixture board of the scenario «A board with a unique solution that the rules cannot finish is not a generator output» is exactly today's `generate(4, 1).givens`, so that scenario is also red today (the givens are equal) and is the regression guard for the old behaviour.

## Data model

No new type. `solveByRules(board: Grid): { solved: boolean; steps: number }` (names are guidance; the tests import it from `src/engine/rule-solve`). `Puzzle` is unchanged: `size`, `givens`, `solution`. No state, no storage (TC-12). Observed side effect on the scratch copy: average givens over seeds 1 to 20 go from 4.7 to 4.3 at N = 4, from 8.3 to 9.2 at N = 6, from 13.2 to 16.6 at N = 8 (no requirement pins the number of givens).

## Error handling strategy

Input validation is untouched: an odd N, N below 4 or above 16, a size that is not an integer, a seed outside 0 to 2147483647 and non-number arguments raise the same errors as before (FR-16, FR-17, FR-49, FR-50, FR-51), checked before any work. The new code adds no throw and no retry loop: the carving loop cannot fail to terminate (at most N^2 attempts, each a finite closure, each of at most N^2 fills), and the fill phase keeps its existing restart behaviour. `solveByRules` on a malformed board is out of contract (the baseline Exclusions already assume well-formed boards). A failure to meet the timing bounds is not handled at run time; it is the stop condition of decision 6.

None. Grep of `tests/` for `generate(` and pinned grids (2026-10-06) found these uses, each unaffected:

- Pin a solution, not givens: `SOLUTION_8_TEXT` in `tests/helpers/play-page.ts` (the 8×8 solution of seed 1), asserted at `tests/play-page-helpers.test.ts` line 106. Unchanged by decision 4.
- The premise `generate(4, 1).givens` differs from `generate(4, 2).givens` (`tests/play-page-size-selector.test.ts` line 114) was checked on the scratch copy and still holds; task 2.4 re-checks it on the real code.

New tests only: `tests/generator-rule-solvable.test.ts` (`@trace FR-27`).

## Risks and mitigations

- **NFR-3 pressure at N = 8** (the plan names it): measured margin is two orders of magnitude on the scratch copy; the stop condition of decision 6 and the 50% tripwire guard it; the bounds are never relaxed.
- **The carving predicate is not monotone in some corner** (a removal accepted, a later state stuck): carving itself does not depend on monotonicity (every removal is re-checked, decision 1); the closed-upward argument in decision 1 is what the partial-board scenario relies on. The FR-27 test checks the final puzzles over 60 puzzles, and the scenario on partial boards (120 boards) checks that consequence from the other side.
- **Random draws shift** and the solutions change: task 2.3 keeps the order; `tests/play-page-helpers.test.ts` line 106 fails loudly if not.
- **Puzzles get denser** (more givens at N = 6 and 8): not a requirement; difficulty is FR-44 (Future). Recorded in `docs/current-state.md`.
- **A hint-engine change later breaks the guarantee** (the check depends on `hint`): the FR-27 test runs against the real `hint` over the seed set, so such a change fails it.
